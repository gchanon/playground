# ex08 — รีวิว PR นี้: concurrent enrichment fetcher

**ประเภท:** Code review · **ผู้เขียน:** เพื่อนร่วมทีม · **Branch:** `feat/bulk-enrichment`

## ที่มา

เราต้อง enrich ข้อมูลหลักร้อย record ต่อหนึ่ง request โดยเรียก endpoint ของ
third-party ทุกวันนี้มันเป็นลูปแบบเรียงทีละตัวและ p99 แย่มาก PR นี้เลยเปลี่ยน
มาใช้ fetcher แบบ concurrent ที่จำกัดจำนวนพร้อมกันไว้

ผู้เขียนบอกว่า: "เทสต์ผ่านบนเครื่อง benchmark ดูดีมาก เร็วขึ้นราว 8 เท่า
ตอนยิง 200 URL"

## สิ่งที่ QA เจอบน staging

- endpoint enrichment ใช้งานได้ และเร็วขึ้นจริง
- `go_goroutines` บน staging pod มีแต่ขึ้นอย่างเดียว เริ่มที่ ~40 หลัง deploy
  และอยู่ที่ ~19,000 หลังผ่านไปสามวัน เมโมรีก็ขึ้นตามกันไป
- กราฟไต่ชันกว่าเดิมมากในวันที่ provider ฝั่ง third-party ไม่เสถียร
- เวลา request ฝั่ง client timeout (ผู้ใช้ปิดแท็บ, gateway ต้นทางเลิกรอ)
  ตัวเลขก็ดูเหมือนจะกระโดดขึ้นด้วย
- ไม่มีอะไรใน log ไม่มี panic ไม่มี error นอกจาก error ฝั่ง upstream ที่คาดไว้อยู่แล้ว

## งานของคุณ

รีวิว `fetcher.go` เหมือนที่คุณจะรีวิว PR จริง ๆ แล้วบอกว่าคุณจะบล็อกไม่ให้ merge
ด้วยเหตุผลอะไรบ้าง เทสต์ใน `fetcher_test.go` คือสิ่งที่ staging กำลังบ่นถึง
เขียนออกมาเป็นโค้ด
