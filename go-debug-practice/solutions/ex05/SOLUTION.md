# ex05 — `wg.Add` อยู่ผิดที่ + loop variable ถูกแชร์ (Go 1.21)

มี **2 บั๊ก** ในฟังก์ชันเดียว และอาการของทั้งสองปนกันจนสับสน

## บั๊กที่ 1 — `wg.Add(1)` อยู่ข้างใน goroutine

```go
for _, shard := range shards {
    go func() {
        wg.Add(1)        // <-- สายเกินไป
        defer wg.Done()
        ...
    }()
}
wg.Wait()               // อาจวิ่งถึงตรงนี้ตอน counter ยังเป็น 0
```

`go func()` แค่ "ฝากงานเข้าคิว" ไม่ได้รันทันที กว่า scheduler จะหยิบ goroutine
ขึ้นมารัน main goroutine อาจไปถึง `wg.Wait()` แล้ว ตอนนั้น counter ยังเป็น 0
`Wait()` จึงคืนทันที → report ได้ข้อมูลไม่ครบ และจบงานเร็วผิดปกติ (~2ms
ทั้งที่ query ตัวเดียวใช้ 1ms) ตรงกับที่ ticket บอก

และเพราะ goroutine ยังเขียน `perShard` อยู่ขณะที่ caller อ่าน
จึงมีโอกาสเจอ `fatal error: concurrent map read and map write`

อุปมา: `WaitGroup` คือ **ใบเซ็นชื่อหน้าห้องประชุม** ที่หัวหน้าใช้นับว่า
"ยังมีใครอยู่ในห้องไหม" ถ้าให้แต่ละคน **เข้าไปในห้องแล้วค่อยเซ็น**
หัวหน้าเดินมาดูใบตอนยังไม่มีใครเซ็น ก็เห็นใบเปล่าแล้วปิดห้องเลย
ต้อง **เซ็นก่อนเดินเข้าห้อง** เสมอ

## บั๊กที่ 2 — loop variable ถูกแชร์ (เฉพาะ Go ≤ 1.21)

```go
for _, shard := range shards {
    go func() {
        ... counter.CountOrders(ctx, shard)   // shard ตัวเดียวกันทุก goroutine
    }()
}
```

ใน Go ตั้งแต่ 1.21 ลงไป `shard` คือตัวแปร **ตัวเดียว** ที่ถูกเขียนทับทุกรอบ
closure จับ "ตัวแปร" ไม่ใช่ "ค่า" ณ ตอนนั้น goroutine ที่เริ่มรันช้า
จึงเห็นค่าของรอบท้าย ๆ → ได้ shard เดิมซ้ำ ๆ หรือได้ `shard-06` ตัวเดียว

อุปมา: เหมือนให้คนงาน 6 คนอ่านคำสั่งจาก **ไวท์บอร์ดแผ่นเดียวกัน**
แทนที่จะแจกใบสั่งงานคนละใบ หัวหน้าลบแล้วเขียนทับไปเรื่อย ๆ
พอคนงานเงยหน้าขึ้นอ่าน ทุกคนก็เห็นคำสั่งอันสุดท้ายเหมือนกันหมด

> **ทำไมแบบฝึกนี้อยู่คนละ module**
> `go.mod` ของโฟลเดอร์นี้ระบุ `go 1.21` ตั้งแต่ **Go 1.22** เป็นต้นไป
> ภาษาเปลี่ยนให้ loop variable เป็นตัวใหม่ทุกรอบ บั๊กนี้จึงหายไปเอง
> ถ้าใช้ `go 1.22+` ใน go.mod
> ทีมที่ยังมีโค้ดเก่า หรือ module ที่ยังไม่ได้อัป `go` directive
> ยังเจอบั๊กนี้ได้อยู่ — ซึ่งเป็นคำตอบที่ดีมากถ้าถูกถาม

## วิธีแก้ (น้อยที่สุด)

```go
 	for _, shard := range shards {
-		go func() {
-			wg.Add(1)
+		wg.Add(1)
+		go func(shard Shard) {
 			defer wg.Done()
 			...
-		}()
+		}(shard)
 	}
```

ทางเลือกสำหรับบั๊กที่ 2: เขียน `shard := shard` เป็นบรรทัดแรกในลูป
(สำนวนเก่าที่เจอบ่อยในโค้ดเบสก่อน Go 1.22) หรืออัป `go` directive
ใน `go.mod` เป็น `1.22` ขึ้นไป

## สิ่งที่ควรพูดตอนสัมภาษณ์

1. **จับเบาะแส "เร็วผิดปกติ"** — งานที่ควรใช้ ~1ms แต่จบใน ~2ms
   ทั้งที่มี 6 shard แปลว่า **เราไม่ได้รอจริง** → มองหา `Wait` ที่ไม่ทำงาน
   นี่คือเบาะแสที่ดีกว่าการไล่อ่านโค้ดทีละบรรทัด
2. **ท่องกฎ `Add` ให้ได้** — "`wg.Add` ต้องถูกเรียกจาก goroutine ที่เรียก
   `wg.Wait()` เสมอ และต้องเรียกก่อน `go`" เป็นประโยคที่ควรพูดออกมาตรง ๆ
3. **ถามเวอร์ชัน Go** — พอเห็น closure จับ loop variable ให้ถามว่า
   "module นี้ `go` directive เป็นเวอร์ชันอะไร" การถามคำถามนี้แสดงว่า
   ตามการเปลี่ยนแปลงของภาษา ไม่ได้ท่องกฎเก่ามาอย่างเดียว
4. **เสนอเครื่องมือ** — `go test -race` จับบั๊กทั้งสองตัวได้ และ
   `go vet` มี `loopclosure` ที่เตือนเคสนี้ (แต่ไม่อยู่ในชุดที่
   `go test` รันให้อัตโนมัติ จึงต้องรัน `go vet ./...` แยก)
5. **อธิบายว่าทำไมอาการถึง "ไม่คงที่"** — bug ที่ขึ้นกับ scheduler
   จะให้ผลต่างกันทุกรอบ ถ้าเจออาการแบบนี้ให้สงสัย concurrency ก่อนเสมอ
   และให้เขียนเทสที่วนซ้ำหลายรอบ (เทสในโจทย์วน 25 รอบ) เพื่อให้มันพังแน่ ๆ
