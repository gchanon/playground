# ex06 — `defer` อยู่ในลูป: คืน semaphore ช้าเกินไป

## บั๊กคืออะไร

```go
for _, job := range jobs {
    select {
    case p.sem <- struct{}{}:        // จองช่อง
    case <-ctx.Done():
        ...
    }
    defer func() { <-p.sem }()       // <-- คืนช่องตอน Run จบ ไม่ใช่ตอน job จบ

    wg.Add(1)
    go func(job Job) { ... }(job)
}
```

`defer` ทำงานตอน **ฟังก์ชันคืนค่า** ไม่ใช่ตอนจบรอบลูป
ดังนั้นช่อง semaphore ที่จองไปจะไม่ถูกคืนเลยจนกว่า `Run` จะจบ

`concurrency = 4`, `jobs = 12`:
- job 1–4 จองครบ 4 ช่อง
- goroutine ทั้ง 4 ทำงานเสร็จ แต่ **ไม่มีใครคืนช่อง**
- job 5 ไปติดที่ `p.sem <- struct{}{}` ค้างอยู่ตรงนั้น
- `Run` ไม่มีวันจบ → `defer` ไม่มีวันทำงาน → ช่องไม่มีวันว่าง

เป็น deadlock แบบคลาสสิก: **คนที่จะปลดล็อกคือคนที่ติดล็อกอยู่เอง**

ในโค้ดนี้ไม่ hang ถาวรเพราะมี `context.WithTimeout(ctx, 10s)` คลุมอยู่
จึงหลุดออกมาเป็น `context deadline exceeded` หลัง 10 วินาที — ตรงกับ ticket

## ทำไมถึงเกิด

อุปมา: semaphore คือ **บัตรคิว 4 ใบ** ที่ต้องถือเข้าห้องทำงาน
เจตนาคือ "ทำงานเสร็จแล้วคืนบัตร" แต่โค้ดนี้เขียนว่า
"คืนบัตรตอน **เลิกงานทั้งกะ**" พอคน 4 คนแรกทำเสร็จแต่ยังกำบัตรไว้
คนที่ 5 ก็ยืนรอหน้าห้องไปเรื่อย ๆ และกะก็ไม่มีวันเลิก เพราะยังรอคนที่ 5

เหตุผลที่คนเขียนพลาด: สำนวน `lock(); defer unlock()` ถูกต้องและปลอดภัยมาก
**ในระดับฟังก์ชัน** พอเอามาวางในลูป ความหมายเปลี่ยนไปคนละเรื่อง
แต่หน้าตาโค้ดดูคุ้นตาจนไม่มีใครสะดุด

เบาะแสจาก ticket ที่ควรจับได้: **"batch เท่ากับ concurrency แล้วทำงานได้
แต่ batch มากกว่าแล้วค้าง"** → ชี้ตรงไปที่กลไกจำกัดจำนวนพร้อมกัน

## วิธีแก้ (น้อยที่สุด)

ย้ายการคืนช่องเข้าไปใน goroutine ที่เป็นเจ้าของงานจริง

```go
-		defer func() { <-p.sem }()
-
 		wg.Add(1)
 		go func(job Job) {
 			defer wg.Done()
+			defer func() { <-p.sem }()
 			...
 		}(job)
```

(จองใน loop, คืนใน worker — คู่กันถูกต้อง และ `defer` ตัวนี้อยู่ใน
ฟังก์ชันของ goroutine จึงทำงานทุกครั้งที่ job จบ รวมถึงตอน panic)

กรณีทั่วไปของ "defer ในลูป" ที่ไม่ใช่ semaphore เช่นเปิดไฟล์ทีละไฟล์
วิธีแก้มาตรฐานคือ **แยกงานต่อหนึ่งรอบออกเป็นฟังก์ชันย่อย** ให้ `defer`
มีขอบเขตเท่ากับหนึ่งรอบ

```go
for _, path := range paths {
    if err := func() error {
        f, err := os.Open(path)
        if err != nil { return err }
        defer f.Close()          // ปิดตอนจบรอบนี้
        return process(f)
    }(); err != nil {
        return err
    }
}
```

## สิ่งที่ควรพูดตอนสัมภาษณ์

1. **ขอ goroutine dump ก่อน** — อาการ "ค้าง" ให้ส่ง `SIGQUIT` หรือเปิด
   `net/http/pprof` แล้วดู `goroutine?debug=2` จะเห็น main goroutine
   ปักอยู่ที่ `chan send` ของ semaphore ทันที ไม่ต้องเดาเลย
2. **อ่าน stack ให้เป็น** — บอกว่า "goroutine ที่ค้างคือ caller เอง
   ไม่ใช่ worker" แปลว่าปัญหาอยู่ที่การจองทรัพยากร ไม่ใช่ที่ sink
3. **พูดกฎของ `defer` ให้ชัด** — "`defer` ผูกกับ function scope
   ไม่ใช่ block scope" แล้วเสริมว่า Go ไม่มี block-scoped defer
   จึงต้องแยกฟังก์ชันย่อยถ้าอยากได้ขอบเขตระดับรอบ
4. **ใช้เบาะแสจาก ticket** — "เพิ่ม concurrency ให้เท่า batch แล้วหาย"
   เป็นการยืนยันสมมติฐานโดยไม่ต้องอ่านโค้ดเลย พูดออกมาให้ interviewer
   เห็นว่าเราใช้ข้อมูลจากหน้างานมาตัดตัวเลือก
5. **ถ้าถูกถามต่อ** — พูดถึง `golang.org/x/sync/errgroup` ที่มี
   `SetLimit(n)` ทำเรื่องนี้ให้แล้ว และจัดการ error กับ ctx ให้ด้วย
