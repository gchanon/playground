# ex03 — `err` ถูกบัง (shadowing) ด้วย `:=` ในลูป retry

## บั๊กคืออะไร

```go
var receipt *Receipt
var err error

for attempt := 1; attempt <= c.maxAttempts; attempt++ {
    receipt, err := c.attempt(ctx, req)   // <-- := สร้างตัวแปรใหม่ 2 ตัว
    ...
}

if err != nil { ... }      // err ตัวนอก — ไม่เคยถูกเซ็ตเลย
return receipt, nil        // receipt ตัวนอก — ยังเป็น nil
```

`:=` ข้างในลูปสร้าง `receipt` กับ `err` **ตัวใหม่** ที่มีอายุแค่ในรอบลูปนั้น
ตัวแปรข้างนอกไม่เคยถูกแตะ พอ retry ครบ 3 ครั้งแล้วยังพัง ลูปจบ
`err` ข้างนอกยังเป็น `nil` → ฟังก์ชัน return `(nil, nil)`

caller เห็น `err == nil` ก็ถือว่าจ่ายเงินสำเร็จ แล้วไป `receipt.TransactionID`
บน nil pointer — ตรงกับอาการใน ticket เป๊ะ: ออเดอร์ขึ้น PAID แบบไม่มี
transaction id บวก pod บางตัว nil pointer dereference

## ทำไมถึงเกิด

Go ยอมให้ประกาศตัวแปรชื่อซ้ำใน scope ที่ลึกกว่าได้ และ **คอมไพล์ผ่าน**
เพราะตัวแปรทั้งตัวนอกตัวในต่างก็ "ถูกใช้งาน" ครบ

อุปมา: เหมือนออฟฟิศมีไวท์บอร์ดกลางชื่อ **"สถานะการจ่ายเงิน"**
พนักงานเดินเข้าห้องประชุมย่อย แล้วเขียนผลลัพธ์ลง **ไวท์บอร์ดในห้องย่อย**
ที่บังเอิญตั้งชื่อเหมือนกัน พอประชุมจบ ห้องย่อยถูกเคลียร์ทิ้ง
หัวหน้าเดินมาดูบอร์ดกลาง — ว่างเปล่า ก็สรุปว่า "ไม่มีปัญหา"

จุดที่หลอกตาที่สุดคือ **`return receipt, nil` ข้างในลูปทำงานถูกต้อง**
(ใช้ `receipt` ตัวใน) เทสเคสที่สำเร็จจึงผ่านหมด บั๊กโผล่เฉพาะตอนที่
ลูปวิ่งจนครบโดยไม่สำเร็จเลย — คือตอน gateway ล่มเท่านั้น

## วิธีแก้ (น้อยที่สุด)

เปลี่ยน `:=` เป็น `=` เพื่อ assign ลงตัวแปรข้างนอก

```go
-		receipt, err := c.attempt(ctx, req)
+		receipt, err = c.attempt(ctx, req)
```

## วิธีจับบั๊กแบบนี้อัตโนมัติ

`go vet` มาตรฐาน **ไม่จับ** shadowing ต้องลงตัวตรวจแยก

```bash
go install golang.org/x/tools/go/analysis/passes/shadow/cmd/shadow@latest
go vet -vettool=$(which shadow) ./...
```

หรือใช้ `golangci-lint` เปิด linter ชื่อ `govet` (`shadow: true`) กับ `nilerr`

## สิ่งที่ควรพูดตอนสัมภาษณ์

1. **ตั้งสมมติฐานจากอาการก่อน** — "return (nil, nil)" คืออาการที่เป็นไปได้
   ไม่กี่แบบ: ลืม assign, shadowing, หรือ early return ที่ลืมใส่ error
2. **ชี้ `:=` กับ `=`** — พูดคำว่า *variable shadowing* ให้ชัด
   แล้วอธิบายว่าทำไมคอมไพเลอร์ไม่เตือน (ตัวแปรถูกใช้ครบทั้งคู่)
3. **อธิบายว่าทำไมเทสเดิมถึงจับไม่ได้** — เพราะเทสที่มีอยู่ครอบคลุมเฉพาะ
   เส้นทางที่สำเร็จ เส้นทาง "ล้มเหลวทุกครั้ง" ไม่เคยถูกเทส
   ให้เสนอเพิ่มเทสเคสนั้นก่อนแก้โค้ด
4. **เสนอ tooling** — การบอกว่าจะเปิด `shadow` ใน CI แสดงว่าคิดถึงการ
   ป้องกันทั้งทีม ไม่ใช่แก้เฉพาะไฟล์นี้
5. **ถ้าถูกถามต่อเรื่อง retry** — ชี้ว่าของเดิมแยก retryable/non-retryable
   ถูกแล้ว (402 ไม่ retry) และควรมี idempotency key เสมอ ซึ่งโค้ดนี้มี
