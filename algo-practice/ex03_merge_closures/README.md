# ex03 — รวมช่วงเวลาที่ร้านปิดรับออเดอร์ (sort + intervals)

**เวลา:** 20 นาที · **ระดับ:** medium

## โจทย์

ร้านหนึ่งตั้ง "ปิดรับออเดอร์ชั่วคราว" ได้หลายช่วงต่อวัน และช่วงพวกนี้อาจทับกัน
ก่อนส่งไปแสดงในแอป ต้องรวมให้เหลือช่วงที่ไม่ทับกันเลย และเรียงตามเวลาเริ่ม

```go
type Interval struct{ Start, End int } // [Start, End) นาทีนับจากเที่ยงคืน

func MergeClosures(in []Interval) []Interval
```

- ช่วงเป็นแบบ **half-open** `[Start, End)` คือรวม Start แต่ไม่รวม End
- ช่วงที่**ชนกันพอดี** (`End` ของอันแรก == `Start` ของอันถัดไป) ต้องรวมเป็นช่วงเดียว เพราะไม่มีช่องว่างให้ร้านเปิดรับเลย
- input ไม่ได้เรียงมา
- **ห้ามแก้ slice ที่รับเข้ามา** เพราะ caller ยังใช้ต่อ

## ตัวอย่าง

| in | ผลที่ถูก |
|---|---|
| `[60,120) [90,180)` | `[60,180)` |
| `[600,660) [60,120) [100,200)` | `[60,200) [600,660)` |
| `[60,120) [120,180)` | `[60,180)` ชนพอดีต้องรวม |
| `[60,120) [121,180)` | ไม่รวม เพราะมีช่องว่าง 1 นาที |
| `[0,100) [10,20) [90,95)` | `[0,100)` |

## ข้อจำกัด

- จำนวนช่วงสูงสุด 200,000
- **เป้า:** O(n log n) เทสมี input ใหญ่ที่จับเวลา 2 วินาที

### ภาพที่ใช้คิด: ระบายสีบนไม้บรรทัดเวลา

แต่ละช่วง = ระบายแถบสีหนึ่งแถบ คำตอบ = ก้อนสีที่ติดกันเป็นผืนเดียว
ถ้าหยิบช่วงมาระบาย**เรียงตามเวลาเริ่ม** ดูแค่**ก้อนล่าสุดก้อนเดียว**ก็พอ ก้อนที่อยู่ซ้ายกว่านั้นไม่มีทางโดนแตะอีกแล้ว

### โค้ดที่ทำผ่าน

```go
func MergeClosures(in []Interval) []Interval {
	if len(in) == 0 {
		return nil
	}

	sorted := make([]Interval, len(in))
	copy(sorted, in)
	sort.Slice(sorted, func(i, j int) bool {
		return sorted[i].Start < sorted[j].Start
	})

	result := []Interval{
		sorted[0],
	}

	for _, intervalData := range sorted[1:] {
		if intervalData.Start <= result[len(result)-1].End {
			if intervalData.End > result[len(result)-1].End {
				result[len(result)-1].End = intervalData.End
			}
		} else {
			result = append(result, intervalData)
		}
	}
	return result
}
```

| จุดที่ต้องระวัง | โค้ดนี้ |
|---|---|
| input ว่าง | `len(in) == 0` คืน `nil` ✅ |
| ห้ามแก้ input | `copy` ไป `sorted` ก่อน sort ✅ |
| ชนพอดีต้องรวม | `<=` ✅ |
| ช่วงซ้อนข้างใน `[0,100) [10,20)` | ขยาย `End` เฉพาะตอนยาวกว่า ✅ |
| Complexity | sort O(n log n) + วนรอบเดียว O(n) = **O(n log n)**, space O(n) |

**Review (ไม่ได้ผิด):**

1. `result[len(result)-1]` ซ้ำ 3 ที่ ตั้งชื่อเป็น **pointer** อ่านง่ายกว่า ต้องมี `&` ไม่งั้นได้สำเนา แก้แล้วไม่มีผล:
   ```go
   last := &result[len(result)-1]
   if intervalData.Start <= last.End {
   	last.End = max(last.End, intervalData.End)
   } else {
   	result = append(result, intervalData)
   }
   ```
2. `slices.SortFunc` เร็วกว่า `sort.Slice` วัด 200,000 ช่วง 3 รอบ: `sort.Slice` 46 ms (4 allocs) กับ `slices.SortFunc` + `cmp.Compare` 32 ms (1 alloc) เร็วกว่า **1.44 เท่า** เพราะ `sort.Slice` สลับของผ่าน reflection ส่วน `slices` ใช้ generics
   ```go
   sorted := slices.Clone(in)
   slices.SortFunc(sorted, func(a, b Interval) int { return cmp.Compare(a.Start, b.Start) })
   ```

### คำถามต่อยอด 1: ต้องใช้ไรเดอร์พร้อมกันมากสุดกี่คน

**โจทย์คนละเรื่องที่ใช้ข้อมูลหน้าตาเดียวกัน:** แต่ละช่วงคือ**งานส่งของ 1 งาน** ไรเดอร์ 1 คนทำได้ทีละงาน ถามว่าต้องมีไรเดอร์อย่างน้อยกี่คน = ช่วงที่**สีซ้อนหนาสุดกี่ชั้น**

| | ข้อ merge | ข้อไรเดอร์ |
|---|---|---|
| ถามอะไร | ตรงไหน**มีสี** | สีซ้อน**หนาสุดกี่ชั้น** |
| `[0,10) [10,20)` ชนพอดี | **รวม** (`<=`) | **ไม่ทับ** คนเดียวส่งเสร็จนาที 10 แล้วรับงานต่อได้ |

**คำตอบรอบแรก:** วน `sorted` แล้วนับงานที่เหลือทุกตัวที่ `Start` ≤ `End` ของงานนี้ ได้ counter สูงสุด

**จุดที่ยังไม่ใช่:**

1. **"ทับกับงานแรก" ไม่ได้แปลว่า "ทับกันเอง"**
   ```
   นาที     0   10  20  30  40        100
   งาน A    [================================)
   งาน B        [===)
   งาน C                [===)
   ```
   นับจาก A ได้ 3 แต่คำตอบจริงคือ **2** เพราะ B จบก่อน C เริ่ม คนทำ B ไปทำ C ต่อได้ ต้องนับงานที่วิ่ง**พร้อมกัน ณ นาทีเดียวกัน**
2. ชนพอดีไม่นับว่าทับ เงื่อนไขต้องเป็น `<` ไม่ใช่ `<=`
3. ลูปในเริ่มใหม่ทุกรอบ = O(n²) งาน 200,000 งานช้าเกิน

**วิธี 1: หัวหน้าจ่ายงาน (min-heap)**

หัวหน้าจดแค่**เวลาส่งเสร็จ**ของไรเดอร์แต่ละคน พองานใหม่มา เช็ก**คนที่เสร็จเร็วสุด**คนเดียว ถ้าคนนี้ยังไม่ว่าง คนอื่นก็ไม่ว่างแน่นอน

```go
// endTimes คือ min-heap ของเวลาส่งงานเสร็จ ข้างในเป็นแค่ []int
type endTimes []int

func (h endTimes) Len() int           { return len(h) }
func (h endTimes) Less(i, j int) bool { return h[i] < h[j] } // เสร็จเร็วกว่าอยู่ใกล้หัวแถว
func (h endTimes) Swap(i, j int)      { h[i], h[j] = h[j], h[i] }
func (h *endTimes) Push(x any)        { *h = append(*h, x.(int)) }
func (h *endTimes) Pop() any {
	old := *h
	n := len(old)
	x := old[n-1]
	*h = old[:n-1]
	return x
}

func MinRiders(jobs []Interval) int {
	sorted := slices.Clone(jobs)
	slices.SortFunc(sorted, func(a, b Interval) int { return cmp.Compare(a.Start, b.Start) })

	onDuty := &endTimes{} // heap ว่าง ยังไม่มีไรเดอร์
	bestRiders := 0
	for _, job := range sorted {
		if onDuty.Len() > 0 && (*onDuty)[0] <= job.Start { // คนที่เสร็จเร็วสุดว่างแล้ว
			heap.Pop(onDuty) // คนนั้นรับงานนี้
		}
		heap.Push(onDuty, job.End)
		bestRiders = max(bestRiders, onDuty.Len())
	}
	return bestRiders
}
```

ไล่ `[0,100) [10,20) [30,40)`:

| งาน | heap ก่อน | คนเสร็จเร็วสุดว่างไหม | heap หลัง | ไรเดอร์ |
|---|---|---|---|---|
| `[0,100)` | ว่าง | เรียกคนเพิ่ม | `[100]` | 1 |
| `[10,20)` | `[100]` | 100 ≤ 10? ไม่ → เรียกเพิ่ม | `[20 100]` | 2 |
| `[30,40)` | `[20 100]` | 20 ≤ 30? **ว่าง** → รับต่อ | `[40 100]` | 2 |

- **pop แค่ครั้งเดียว:** หัวหน้าไม่ไล่ใครออก คนว่างยังอยู่ใน heap รอรับงาน ขนาด heap = จำนวนไรเดอร์ที่เคยเรียกมา และโตเฉพาะตอนทุกคนยุ่งจริง
- **`&endTimes{}`** คือ slice ว่าง (ไม่ใช่ struct) ต้องเป็น pointer เพราะ `Push`/`Pop` เปลี่ยนความยาว ต้องแก้ป้ายตัวจริง
- **`(*onDuty)[0]`** แอบดูหัวแถว O(1) ต้อง `*` เพราะเป็น pointer

**`container/heap` ฉบับย่อ:**

- heap = slice ที่รับประกันแค่ว่า**ตัวแรกน้อยสุด** (ไม่ได้เรียงทั้งหมด) ลูกของ `i` อยู่ที่ `2i+1`, `2i+2`
- เราเขียน 5 method เป็น**มือ**: `Len`, `Less`, `Swap`, `Push` (ต่อท้ายเฉยๆ), `Pop` (ตัดท้ายเฉยๆ)
- Go เป็น**สมอง**: `heap.Push` ต่อท้ายแล้วลอยขึ้น, `heap.Pop` สลับหัวกับท้ายแล้วจมลง ทั้งคู่ O(log n)
- **เรียก `heap.Push(h, x)` เสมอ** ถ้าเรียก `h.Push(x)` ตรงๆ จะต่อท้ายเฉยๆ หัวแถวผิด และ compiler ไม่เตือน
- min-heap ใช้ `<` ใน `Less`, max-heap ใช้ `>`
- `range` ทั้ง heap ไม่ได้ลำดับที่เรียง ต้อง `heap.Pop` ทีละตัว, `heap.Pop` ตอนว่าง = panic, แก้ค่าในคิวแล้วต้อง `heap.Fix(h, i)`

**วิธี 2: เดินตามเวลา นับความหนาของสี (sweep line)**

```go
func MinRidersSweep(jobs []Interval) int {
	starts := make([]int, len(jobs))
	ends := make([]int, len(jobs))
	for i, job := range jobs {
		starts[i] = job.Start
		ends[i] = job.End
	}
	slices.Sort(starts)
	slices.Sort(ends)

	working, bestRiders := 0, 0
	e := 0
	for _, start := range starts {
		for ends[e] <= start { // งานที่ส่งเสร็จแล้ว ณ นาทีนี้ (ชนพอดีก็ว่าง)
			working--
			e++
		}
		working++
		bestRiders = max(bestRiders, working)
	}
	return bestRiders
}
```

**ทำไมลูปซ้อนแต่เป็น O(n log n):** `e` ประกาศ**นอก**ลูปและเดินหน้าอย่างเดียว (two pointers) ตลอดทั้งฟังก์ชันขยับรวมไม่เกิน n ครั้ง ลูปทั้งหมดจึง O(n) ส่วน log n มาจาก sort สองครั้ง

> วิธีเช็กเร็ว: ตัวแปรของลูปในประกาศ**ใน**ลูปนอก (`j := i + 1`) = เริ่มใหม่ทุกรอบ ระวัง O(n²) ประกาศ**นอก**แล้วเดินหน้าอย่างเดียว = มักเป็น O(n)

**ทำไมกล้า sort start กับ end แยกกัน:** คำถามสนใจแค่ "นาทีนี้มีงานวิ่งกี่งาน" ซึ่ง

> งานที่วิ่งอยู่ ณ นาที t = (จำนวน Start ≤ t) − (จำนวน End ≤ t)

งานที่เสร็จแล้วถูกนับทั้งสองฝั่งจึงหักล้างกัน เหลือแค่งานที่กำลังวิ่ง ไม่ต้องรู้ว่า End ไหนเป็นของงานไหน (เหมือนนับคนในห้องด้วยเครื่องนับประตูเข้ากับประตูออก)
ตัวอย่าง `[0,100) [10,20) [30,40)` กับ `[0,20) [10,40) [30,100)` เป็นงานคนละชุด แต่ starts/ends เหมือนกัน คำตอบเท่ากัน (2)
จุดเดียวที่ลำดับสำคัญคือเวลาเท่ากัน ต้องหัก End ก่อน (`<=`) ตามกติกา half-open

| คำถาม | แยก sort ได้ไหม |
|---|---|
| ต้องใช้ไรเดอร์มากสุดกี่คน | ✅ sweep |
| ไรเดอร์**คนไหน**รับงาน**ไหน** | ❌ heap ที่เก็บ `(End, riderID)` |
| งาน**ไหน**ทับกับงาน**ไหน** | ❌ |

| | heap | sweep |
|---|---|---|
| time | O(n log n) | O(n log n) |
| วัด 200,000 งาน (รอบเดียว) | 57 ms | 41 ms |
| เหมาะกับ | งานเข้าทีละงาน, ต้องรู้ตัวตนไรเดอร์ | มีงานครบชุดแล้ว, โค้ดสั้น |

ทดสอบแล้ว: ทั้งสองวิธีตรงกับ brute force (เช็กทุกจุด Start) บน input สุ่ม 5,000 ชุด และไม่แก้ input

### คำถามต่อยอด 2: แทรกช่วงใหม่ใน list ที่รวมไว้แล้ว

**คำตอบรอบแรก:** binary search หาตำแหน่งจาก `Start` แล้วแทรกลง slice ✅ ถูกครึ่งหนึ่ง

**ที่ขาด:**

1. **แทรกแล้วต้องรวมกับเพื่อนบ้าน** ช่วงใหม่ช่วงเดียวกลืนได้หลายช่วง
   ```
   เดิม:     [60,120)  [200,300)  [400,500)
   ช่วงใหม่:     [100,         450)
   ผลที่ถูก: [60,500)
   ```
2. **แทรกกลาง slice ไม่ฟรี** ต้องเลื่อน/copy ทุกตัวข้างหลัง = O(n) ทั้งข้อจึงเป็น **O(n)** ไม่ใช่ O(log n) (ยังดีกว่า sort ใหม่ O(n log n))

**เฉลย:** list ที่รวมแล้วไม่มีช่วงทับกัน ทั้ง `Start` และ `End` จึง**เรียงจากน้อยไปมาก**ทั้งคู่ binary search ได้ทั้งสองค่า หาขอบ 2 ข้างของ "ช่วงที่โดนกลืน" แล้วรวมเป็นก้อนเดียว

```go
// InsertClosure แทรก x ลงใน merged ที่เรียงและรวมไว้แล้ว คืน slice ใหม่ (ไม่แก้ของเดิม)
func InsertClosure(merged []Interval, x Interval) []Interval {
	// left = ช่วงแรกที่ปลาย "ถึง" จุดเริ่มของ x (ชนพอดีก็นับ เพราะต้องรวม)
	left := sort.Search(len(merged), func(i int) bool {
		return merged[i].End >= x.Start
	})
	// right = ช่วงแรกที่เริ่ม "หลัง" ปลายของ x แบบมีช่องว่าง → ตั้งแต่ตรงนี้ไปไม่โดนกลืน
	right := sort.Search(len(merged), func(i int) bool {
		return merged[i].Start > x.End
	})

	// merged[left:right] คือทุกช่วงที่ทับหรือชนกับ x → รวมเป็นก้อนเดียว
	if left < right {
		x.Start = min(x.Start, merged[left].Start)
		x.End = max(x.End, merged[right-1].End)
	}

	result := make([]Interval, 0, len(merged)-(right-left)+1)
	result = append(result, merged[:left]...)
	result = append(result, x)
	result = append(result, merged[right:]...)
	return result
}
```

- `sort.Search(n, f)` คืน**index แรกที่ `f` เป็น true** (f ต้องเป็น false…false true…true) เป็นตัวช่วย binary search ที่อ่านง่ายที่สุดเวลาเงื่อนไขไม่ใช่ "เท่ากับ"
- ไล่ตัวอย่างข้างบน: `left` = 0 (`[60,120)` ปลาย 120 ≥ 100), `right` = 3 (ไม่มีช่วงไหนเริ่มหลัง 450) → กลืน `merged[0:3]` ทั้งหมด ได้ `[60,500)`
- ไม่ทับใครเลย (เช่น `[130,150)`) → `left == right` แทรกตรงกลางเฉยๆ
- ถ้าเป็นเจ้าของ slice เอง ใช้ `slices.Replace(merged, left, right, x)` แก้ในที่ได้ แต่จะแก้ backing array ของ caller (ดูข้อ 3)

| | time | วัด 200,000 ช่วง แทรก 1 ช่วง (3 รอบ) |
|---|---|---|
| append แล้ว `MergeClosures` ใหม่ | O(n log n) | 4.5–4.7 ms |
| `InsertClosure` | O(log n) หา + O(n) copy = **O(n)** | 0.17–0.28 ms (เร็วกว่า **16–28 เท่า**) |

ทดสอบแล้ว: เทียบกับ "append แล้ว merge ใหม่" บน input สุ่ม 20,000 ชุด ตรงกันหมด และไม่แก้ input

**ถ้าแทรกบ่อยมาก:** O(n) ต่อครั้งยังแพง ต้องเปลี่ยนโครงสร้างเป็น tree ที่เรียงตัวเอง (balanced BST / skip list) แทรกได้ O(log n) Go standard library ไม่มีให้ ต้องใช้ library ภายนอก

### คำถามต่อยอด 3: ทำไมห้ามแก้ slice ที่รับเข้ามา

**คำตอบ:** ✅ ถูก — `in` คือป้ายบอกว่า backing array อยู่ไหน, len, cap ถ้า sort ตรงๆ จะสลับของใน backing array ตัวเดียวกับที่ caller ใช้อยู่

**เติม:**

- **ป้ายถูก copy แต่ของในโกดังไม่ถูก copy:** sort สลับของในโกดังเดียวกัน caller เห็นลำดับเปลี่ยน แต่ถ้าฟังก์ชัน `append`/re-slice `in` caller **ไม่เห็น** len ใหม่ เพราะแก้แค่ป้ายสำเนา
- **ผลในงานจริง:** caller เก็บช่วงตามลำดับที่ร้านกรอกไว้โชว์ในหน้าตั้งค่า เรียกฟังก์ชันนี้ครั้งเดียว ลำดับหน้าตั้งค่าเปลี่ยนเอง บั๊กหายากเพราะฝั่ง caller ไม่มีบรรทัดไหนสั่งเรียงเลย ถ้ามี goroutine อื่นอ่าน slice นี้อยู่ด้วยจะกลายเป็น **data race**

### สรุปสิ่งที่ต้องฝึกเพิ่มจากข้อนี้

1. โจทย์ intervals มีหลายแบบที่ข้อมูลหน้าตาเหมือนกัน: **รวม** (ตรงไหนมีสี) กับ **นับซ้อน** (หนากี่ชั้น) เงื่อนไขชนพอดีกลับทางกัน
2. ลองหา**ตัวอย่างค้าน**ก่อนเชื่อวิธีนับ: "ทับกับ A" ≠ "ทับกันเอง"
3. อ่าน complexity จาก**จำนวนครั้งที่ pointer ขยับรวม** ไม่ใช่จำนวนลูปซ้อน
4. หาตำแหน่งได้ O(log n) ไม่ได้แปลว่าแทรกได้ O(log n) ใน slice
5. เรียก `heap.Push`/`heap.Pop` ผ่าน package เสมอ
