# ex04 — อีกกี่วันเบี้ยประกันจะแพงขึ้น (monotonic stack)

**เวลา:** 20 นาที · **ระดับ:** medium

## โจทย์

ระบบเปรียบเทียบประกันเก็บเบี้ยรายวันของแผนหนึ่งไว้ อยากแสดงในหน้าแอปว่า
"ถ้าซื้อวันนี้ อีกกี่วันราคาจะ**สูงกว่า**วันนี้" เพื่อกระตุ้นให้ซื้อเร็ว

```go
func DaysUntilHigher(premiums []int) []int
```

- `result[i]` = จำนวนวันที่ต้องรอจากวัน `i` จนเจอวันที่ราคา**มากกว่า**วัน `i` จริงๆ
- ราคา**เท่ากันไม่นับ**ว่าสูงกว่า
- ถ้าหลังจากนั้นไม่มีวันไหนแพงกว่าเลย ให้เป็น `0`
- `len(result) == len(premiums)`

## ตัวอย่าง

| premiums | ผลที่ถูก |
|---|---|
| `73 74 75 71 69 72 76 73` | `1 1 4 2 1 1 0 0` |
| `5 5 5 6` | `3 2 1 0` |
| `30 10 20 40` | `3 1 1 0` |

## ข้อจำกัด

- `len(premiums)` สูงสุด 200,000
- **เป้า:** O(n) เทสมี input ใหญ่ที่จับเวลา 2 วินาที

3. ถ้าข้อมูลมาแบบ stream ทีละวัน จะตอบคำถามนี้ได้ทันทีไหม เพราะอะไร

## บันทึกหลังทำ (14 ต.ค. 2026)

### premium คืออะไร

**เบี้ยประกัน** = ราคาที่ลูกค้าจ่ายซื้อกรมธรรม์ มองเป็น "ราคาสินค้ารายวัน" ก็ได้ ตัวโจทย์ไม่ได้ใช้ความรู้เรื่องประกันเลย

### ภาพที่ใช้คิด: ตึกเรียงกันมองไปทางขวา

ราคาแต่ละวัน = ตึกสูงเท่าราคา คำถาม = **"ตึกแต่ละหลัง ต้องมองไปทางขวากี่หลังถึงเจอตึกที่สูงกว่าตัวเอง"**

**ไอเดีย 1 — ไม่ให้ตึกเก่ามองหา ให้ตึกใหม่เดินมาบอก:**
วิธีตรงๆ (ทุกตึกมองไปข้างหน้าเอง) กับราคาที่ลดลงเรื่อยๆ 200,000 วัน ต้องมองรวมราว n²/2 = 2 หมื่นล้านครั้ง
กลับด้าน: เดินซ้ายไปขวา ตึกที่ยังไม่เจอตึกสูงกว่ายืนรอใน `waiting` พอตึกใหม่มา ก็บอกตึกที่รออยู่ซึ่งเตี้ยกว่าว่า "เจอแล้ว" ตึกพวกนั้นได้คำตอบและออกจากแถวรอ
ตึกใหม่เป็นตึกสูงกว่า**ตัวแรก**ที่ตึกเก่าเจอแน่นอน เพราะถ้ามีตัวก่อนหน้าที่สูงกว่า ตึกเก่าคงออกจากแถวไปแล้ว

**ไอเดีย 2 — แถวรอเรียงจากสูง (ซ้าย) ไปเตี้ย (ขวา) เสมอ:**
ถ้าตึกเตี้ยอยู่ซ้ายของตึกสูงในแถวรอ ตอนตึกสูงเข้ามามันต้องบอกตึกเตี้ยไปแล้ว จึงเกิดไม่ได้
ผลคือตึกใหม่เช็กจาก**ตัวขวาสุด** (เตี้ยสุด) ก่อน: เตี้ยกว่า → บอกแล้วเอาออก เช็กตัวถัดไป, ไม่เตี้ยกว่า → **หยุดทันที** ตัวที่ลึกกว่าสูงกว่าอีก

ไล่ `73 74 75 71 69 72 76 73` (เขียน `วัน(ราคา)`):

| วันใหม่ | waiting ก่อน | ตอบใคร | waiting หลัง |
|---|---|---|---|
| 0 (73) | `[]` | – | `[0(73)]` |
| 1 (74) | `[0(73)]` | วัน 0 = 1 | `[1(74)]` |
| 2 (75) | `[1(74)]` | วัน 1 = 1 | `[2(75)]` |
| 3 (71) | `[2(75)]` | 71 > 75? ไม่ | `[2(75) 3(71)]` |
| 4 (69) | `[2(75) 3(71)]` | 69 > 71? ไม่ | `[2(75) 3(71) 4(69)]` |
| 5 (72) | `[2(75) 3(71) 4(69)]` | วัน 4 = 1, วัน 3 = 2, ชน 75 หยุด | `[2(75) 5(72)]` |
| 6 (76) | `[2(75) 5(72)]` | วัน 5 = 1, วัน 2 = 4 | `[6(76)]` |
| 7 (73) | `[6(76)]` | 73 > 76? ไม่ | `[6(76) 7(73)]` |

จบแล้ววัน 6, 7 ยังรอ = ไม่มีวันแพงกว่า คำตอบ 0 (ค่าเริ่มต้นจาก `make` อยู่แล้ว) ผล `1 1 4 2 1 1 0 0`

ท่านี้ชื่อ **monotonic stack** (stack ที่ค่าข้างในเรียงทางเดียวเสมอ)

### โค้ด

```go
func DaysUntilHigher(premiums []int) []int {
	result := make([]int, len(premiums))
	waiting := []int{} // index ของวันที่ยังไม่เจอวันแพงกว่า ราคาจากล่างขึ้นบนไม่เพิ่มขึ้น
	for today, price := range premiums {
		for len(waiting) > 0 && premiums[waiting[len(waiting)-1]] < price {
			day := waiting[len(waiting)-1]
			waiting = waiting[:len(waiting)-1]
			result[day] = today - day
		}
		waiting = append(waiting, today)
	}
	return result // วันที่ยังค้างใน waiting ไม่มีวันแพงกว่า = 0 อยู่แล้ว
}
```

**อ่านทีละส่วน:**

| โค้ด | อ่านว่า | ตอน `waiting = [2 3 4]` |
|---|---|---|
| `len(waiting) > 0` | ยังมีตึกรออยู่ไหม | 3 > 0 ✅ |
| `waiting[len(waiting)-1]` | **ดู**ตัวบนสุด (ท้าย slice) ต้อง −1 เพราะ index เริ่มที่ 0 | `waiting[2]` = วัน 4 |
| `premiums[waiting[len(waiting)-1]]` | เอาเลขวันไปเปิดราคา | `premiums[4]` = 69 |
| `waiting = waiting[:len(waiting)-1]` | **เอาวันที่เพิ่งได้คำตอบออก** (`[:k]` = ถึงก่อน index k) | `[2 3]` |

- **จด index อย่างเดียวพอ:** ได้ทั้งเลขวัน (คิด `today - day`) และราคา (`premiums[day]`)
- **`len(waiting) > 0` ต้องอยู่ซ้ายของ `&&`:** Go เช็กซ้ายก่อน ถ้า false ไม่ดูขวา (short-circuit) กัน `waiting[-1]` panic ตอนแถวว่าง
- **อ่าน `day` ก่อนตัดออก** ถ้าตัดก่อนจะได้วันที่อยู่ถัดลงไป จดคำตอบผิดวัน
- **ต้องใช้ `=` ไม่ใช่ `:=`** `waiting := waiting[:…]` ในลูปสร้างตัวแปรใหม่ (shadowing) ตัวนอกไม่หด → compile ไม่ผ่าน (`declared and not used`) หรือถ้าบังเอิญถูกใช้ = ลูปไม่รู้จบ
- **"ตัดออก" ไม่ได้ลบของในโกดัง** แค่ลด len บนป้าย ช่องนั้นจะถูก `append` ครั้งถัดไปเขียนทับ ไม่ต้องจอง memory ใหม่

### ⚠️ ทำไมเทสจับเวลายังไม่ผ่าน: `fmt.Println` ที่ใส่ debug ไว้

โค้ดถูกแล้ว แต่ในไฟล์ยังมี `fmt.Println(... waiting)` อยู่ในลูปใน เทส input ใหญ่คือราคาลดลง 199,999 วันแล้วพุ่งวันสุดท้าย วันสุดท้ายต้อง pop 199,999 ครั้ง และ**ทุกครั้งพิมพ์ `waiting` ทั้งก้อน** (ยาวเป็นแสน) รวมเป็นตัวเลขที่ต้องพิมพ์ราว n²/2 = 2 หมื่นล้านตัว

| (copy โค้ดไปวัดใน scratchpad, input เดียวกับเทส) | เวลา |
|---|---|
| ลบ `fmt.Println` 3 บรรทัดออก | **3.5 ms** |
| มี `fmt.Println` | **เกิน 5 นาที** (สั่งหยุดเอง) |

บทเรียน: **debug print ก็มี complexity** การพิมพ์ทั้ง slice ในลูปทำให้ O(n) กลายเป็น O(n²) ลบ 3 บรรทัดกับ `import "fmt"` แล้วเทสจะผ่าน

### คำถามต่อยอด (ยังไม่ได้คุยกัน ลองตอบเองก่อนอ่าน)

**1. ถ้าต้องการ "อีกกี่วันจะถูกลง"**
เปลี่ยน `<` เป็น `>` ที่เดียว: ตึกใหม่ไป "บอก" ตึกที่**สูงกว่า**ตัวเอง แถวรอจะเรียงกลับทาง (เตี้ยซ้าย สูงขวา)
```go
for len(waiting) > 0 && premiums[waiting[len(waiting)-1]] > price {
```
ตรวจแล้ว: ตรงกับ brute force บน input สุ่ม 5,000 ชุด (มีราคาซ้ำด้วย)

**2. ทำไม O(n) ทั้งที่มีลูปซ้อน**
นับว่าแต่ละวัน "ถูกแตะ" กี่ครั้ง: ทุกวันถูก `append` เข้า 1 ครั้ง และถูกตัดออก**ไม่เกิน** 1 ครั้ง (ออกแล้วไม่กลับเข้ามาอีก) ลูปในทั้งหมดจึงทำงานรวมไม่เกิน n ครั้ง ตลอดทั้งฟังก์ชัน = O(n) amortized
วัดกับ input ของเทส (แย่สุด): push 200,000 ครั้ง, pop 199,999 ครั้ง — วันสุดท้ายวันเดียว pop เกือบทั้งหมด แต่เพราะทุกตัวออกได้ครั้งเดียว รวมทั้งหมดยังเป็น ~2n
(หลักเดียวกับนิ้ว `e` ในข้อ ex03 ไรเดอร์ และหางหนอนใน ex02)
space: แย่สุด O(n) เมื่อราคาลดลงเรื่อยๆ ทุกวันค้างใน `waiting`

**3. ข้อมูลมาแบบ stream ตอบได้ทันทีไหม**
**ไม่ได้** สำหรับวันนี้ เพราะคำตอบของวันนี้ขึ้นกับ**อนาคต** ต้องรอจนมีวันที่แพงกว่าเข้ามา
- ที่ทำได้: โครงสร้างเดิมใช้กับ stream ได้เลย ตอน pop วันไหนออก = รู้คำตอบวันนั้น**ณ วินาทีนั้น** ส่งออกไปได้ทันที (เช่น ยิง event "วันที่ 3 = 2")
- วันที่ยังอยู่ใน `waiting` = "ยังไม่รู้" ส่วนคำตอบ 0 ("ไม่มีวันแพงกว่าเลย") **ยืนยันได้ตอน stream จบเท่านั้น**
- memory: ถ้าราคาลดลงยาวๆ `waiting` โตไม่หยุด งานจริงมักจำกัดว่าดูล่วงหน้าแค่ k วัน (เช่น 30 วัน) แล้วตัดวันที่เก่ากว่านั้นออกจากก้นแถวเป็น "ไม่เกิน 30 วันไม่แพงขึ้น" — ตัดจากก้นแถวต้องใช้ deque ไม่ใช่ stack

### สรุปสิ่งที่ต้องฝึกเพิ่มจากข้อนี้
1. โจทย์ "หาตัวถัดไปที่มากกว่า/น้อยกว่า" (next greater element) = monotonic stack
2. กลับมุมมอง: แทนที่ของเก่าจะมองหาอนาคต ให้ของใหม่มา "ตอบ" ของเก่าที่รออยู่
3. เช็กว่าลูปในเป็น O(n²) จริงไหม ด้วยการนับว่าแต่ละตัวเข้า/ออกกี่ครั้ง
4. ลบ debug print ก่อนรันเทสจับเวลา พิมพ์ทั้ง slice ในลูป = ซ่อน O(n²)
