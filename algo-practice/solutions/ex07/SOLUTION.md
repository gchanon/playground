# ex07 — LRU cache (map + doubly linked list)

## ทำไมต้องสองโครงสร้าง

| ต้องการ | map อย่างเดียว | list อย่างเดียว | **map + list** |
|---|---|---|---|
| หา key ใน O(1) | ✅ | ❌ ต้องไล่ทั้งแถว | ✅ |
| รู้ว่าใครเก่าสุด O(1) | ❌ map ไม่มีลำดับ | ✅ ท้ายแถว | ✅ |
| ย้ายคนไปหัวแถว O(1) | ❌ | ✅ ถ้ามี pointer ถึงตัวเขา | ✅ map ให้ pointer |

อุปมา: **แถวคิวหน้าร้าน** (list) คนใช้ล่าสุดยืนหัวแถว คนเก่าสุดยืนท้ายแถว
และมี**สมุดรายชื่อ** (map) ที่บอกว่าแต่ละคนยืนอยู่ตรงไหนในแถว จึงเดินไปดึงคนนั้นมาหัวแถวได้ทันทีโดยไม่ต้องไล่หา

`container/list` ของ Go คือ doubly linked list ที่มี `MoveToFront`, `PushFront`, `Back`, `Remove` ให้แล้ว ทุกตัวเป็น O(1)

## โครง

```go
type entry struct { key string; value int }   // ต้องเก็บ key ไว้ด้วย!

type Cache struct {
    capacity int
    order    *list.List                 // หัว = ใช้ล่าสุด, ท้าย = เก่าสุด
    items    map[string]*list.Element   // key → ตำแหน่งในแถว
}
```

**ทำไม entry ต้องมี key:** ตอนไล่คนท้ายแถวออก ต้องลบออกจาก map ด้วย ถ้าเก็บแค่ value จะไม่รู้ว่าต้องลบ key ไหน (ข้อนี้คนลืมบ่อยที่สุด)

## จุดที่คนพลาด

| พลาด | ผล / เทสที่จับ |
|---|---|
| `Get` ไม่ย้ายไปหัวแถว | EvictsLeastRecentlyUsed |
| `Put` key เดิมแล้วเพิ่มเป็นตัวใหม่ ไม่ได้แก้ตัวเดิม | PutExistingKeyUpdatesAndRefreshes (Len เป็น 3) |
| ไล่ออกจาก list แต่ลืม `delete` จาก map | Len ผิด / Get ยังเจอ key ที่ถูกไล่ |
| ไล่ออกก่อนเช็กว่าเป็น key เดิม | ตอนเต็ม แค่อัปเดต key เดิมก็ไปไล่คนอื่นออกโดยไม่จำเป็น |
| เก็บลำดับใน slice | ถูก แต่ย้ายตำแหน่ง O(n) เทส 500,000 ครั้งเกิน 3 วินาที (วัดแล้ว) |

## โค้ด

ดู `lru.go`

## Complexity

- `Get` และ `Put` เป็น O(1), หน่วยความจำ O(capacity)

## พูดในห้องสัมภาษณ์

> "ผมต้องการสองอย่างใน O(1): หา key กับรู้ว่าใครเก่าสุด เลยใช้ map คู่กับ doubly linked list
> map ชี้ไปที่ node ใน list ทำให้ย้ายไปหัวแถวได้ทันที ตอนเต็มก็ตัดท้ายแถว และเก็บ key ไว้ใน node เพื่อลบออกจาก map ได้"

## คำตอบคำถามต่อยอด

1. **หลาย goroutine:** ใช้ `sync.Mutex` ครอบทุก method **ห้ามใช้ `RLock` ใน `Get`** เพราะ `Get` เรียก `MoveToFront` ซึ่งแก้ pointer ใน list = เขียน ถือป้าย "มาดู" แต่แอบแก้ = data race (กับดักเดียวกับเพจ sync บท 3.6) ถ้าคอขวดที่ล็อก ให้แบ่ง cache เป็นหลาย shard ตาม hash ของ key
2. **TTL 5 นาที:** เก็บ `expiresAt` ใน entry ตอน `Get` ถ้าหมดอายุให้ลบแล้วคืนว่าไม่เจอ (lazy) ถ้าห่วงว่าของหมดอายุจะค้างเปลืองหน่วยความจำ เพิ่ม goroutine เก็บกวาดเป็นระยะ (และต้องหยุดมันได้ด้วย ctx ไม่งั้น leak แบบ ex08)
3. **10 เครื่อง:** แต่ละเครื่องมี cache ของตัวเอง hit rate ต่ำลง ข้อมูลไม่ตรงกันระหว่างเครื่อง และ invalidate ยาก ย้ายไป Redis เมื่อต้องการให้ทุกเครื่องเห็นตรงกัน หรือข้อมูลใหญ่เกินหน่วยความจำ แลกกับการต้องเรียกผ่าน network ทุกครั้ง หลายระบบใช้สองชั้น: cache ในเครื่องอายุสั้น ทับบน Redis
4. **1,000 request พร้อมกันตอน cache ว่าง (cache stampede):** ทั้ง 1,000 ตัวจะยิงไปพาร์ทเนอร์พร้อมกัน ใช้ `golang.org/x/sync/singleflight` ให้ key เดียวกันยิงจริงแค่ครั้งเดียว ที่เหลือรอผลเดียวกัน
