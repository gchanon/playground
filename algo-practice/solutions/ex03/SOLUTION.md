# ex03 — รวมช่วงปิดรับออเดอร์ (sort + intervals)

## แนวคิด: เรียงก่อน แล้วเดินรวม

อุปมา: เอา**แถบกระดาษ**ที่แต่ละแผ่นคือช่วงปิดร้าน มาวางเรียงตามจุดเริ่มบนไม้บรรทัด
แล้วเดินจากซ้ายไปขวา ถือแผ่นล่าสุดไว้ในมือ:
- แผ่นถัดไป**เริ่มก่อนหรือพอดีกับ**ปลายแผ่นในมือ (`cur.Start <= last.End`) → ต่อเทปรวมกัน ปลายใหม่ = ปลายที่ไกลกว่า
- ไม่งั้น → วางแผ่นในมือลง หยิบแผ่นใหม่

ทำไมต้องเรียงก่อน: พอเรียงตาม Start แล้ว ช่วงที่ทับกันจะ**อยู่ติดกันเสมอ** เดินรอบเดียวพอ

## จุดที่คนพลาด

| พลาด | ผล | เทสที่จับ |
|---|---|---|
| ใช้ `<` แทน `<=` | ช่วงที่ชนพอดีไม่รวม | touching windows merge |
| `last.End = cur.End` ไม่ใช้ `max` | ช่วงที่ซ้อนอยู่ข้างในไปหดปลายช่วงใหญ่ | nested, later start earlier end |
| `sort.Slice(in, ...)` ตรงๆ | **สลับลำดับใน slice ของ caller** เพราะ slice ชี้ไปที่ array เดียวกัน | DoesNotModifyInput |
| `last := out[len(out)-1]` (ไม่ใช่ pointer) | แก้สำเนา ค่าใน `out` ไม่เปลี่ยน | overlap |

## โค้ด

ดู `merge.go` (เรียงบน `slices.Clone(in)` และใช้ `last := &out[len(out)-1]`)

## Complexity

- เวลา O(n log n) จากการเรียง ส่วนเดินรวมแค่ O(n)
- หน่วยความจำ O(n) สำหรับสำเนา

## พูดในห้องสัมภาษณ์

> "ผมจะเรียงตามเวลาเริ่ม ช่วงที่ทับกันจะมาอยู่ติดกัน แล้วเดินรวมรอบเดียว ใช้ `<=` เพราะเป็น half-open ที่ชนพอดีก็ไม่มีช่องว่าง
> และผมจะ clone ก่อนเรียง เพราะ sort ใน Go แก้ backing array ที่ caller ใช้ร่วมอยู่"

## คำตอบคำถามต่อยอด

1. **ต้องใช้ไรเดอร์พร้อมกันมากสุดกี่คน:** แตกแต่ละช่วงเป็นเหตุการณ์ (Start, +1) และ (End, −1) เรียงตามเวลา ถ้าเวลาเท่ากันให้ −1 มาก่อน (half-open: จบแล้วคนเดิมรับงานใหม่ได้) แล้วไล่บวกสะสม ค่าสูงสุดคือคำตอบ O(n log n)
2. **แทรกช่วงใหม่ใน list ที่รวมไว้แล้ว:** binary search หาตำแหน่ง O(log n) แล้วรวมกับเพื่อนบ้านที่ทับ แต่การแทรกกลาง slice ยังต้อง copy O(n) ถ้าแทรกบ่อยมากใช้ balanced tree หรือ skip list
3. **ทำไมห้ามแก้ input:** slice คือ (pointer, len, cap) ที่ชี้ array เดียวกับของ caller `sort` บน slice ที่รับมาจะสลับข้อมูลของ caller ด้วย ถ้า caller ใช้ลำดับเดิมอยู่ (เช่น index ตรงกับอีก slice หนึ่ง) จะเกิดบั๊กเงียบที่หายาก
