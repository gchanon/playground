# phpdemo

เรียน PHP จากจุดที่เขียน Go เป็นอยู่แล้ว — ด้วยการ **วัดจริง** ไม่ใช่ท่องตำรา
เขียนคู่กับ `chandemo` / `gmpdemo` / `pgdemo` ในสไตล์เดียวกัน

เป้าหมายไม่ใช่ "เขียน PHP ให้คล่อง" ใน 2 วัน แต่คือ **อธิบายได้ว่า PHP ต่างจาก Go ตรงไหน
ในเชิง runtime และความต่างนั้นบังคับให้สถาปัตยกรรมต่างกันยังไง** — ซึ่งเป็นสิ่งที่คนสัมภาษณ์
ระดับ senior ถาม ไม่ใช่ syntax

```bash
brew install php                        # ครั้งเดียว (macOS ไม่มี PHP มาให้แล้วตั้งแต่ 12.3)
cd pgdemo && docker compose up -d       # ใช้ PG ตัวเดียวกับ pgdemo ไม่ต้องเปิดใหม่
cd ..

php phpdemo/demo.php                    # demo ที่รันจบในโปรเซสเดียว
php phpdemo/demo.php -demo value        # รันทีละตัว: syntax | value | memory

bash phpdemo/run.sh                     # demo ฝั่ง HTTP ทั้งหมด (ใช้เวลา ~3 นาที)
bash phpdemo/run.sh pool                # รันทีละตัว: lifecycle | ping | cpu | pool | worker | opcache
WORKERS=4 bash phpdemo/run.sh worker    # เปลี่ยนจำนวน PHP worker
```

## demo ทั้ง 9 ตัว

| สั่ง | ตอบคำถามว่า |
|---|---|
| `demo.php -demo syntax` | อ่าน PHP ให้ออกด้วยความรู้ Go ที่มีอยู่ ภายใน 20 นาที |
| `demo.php -demo value` | ทำไม array ที่ส่งเข้าฟังก์ชันแล้วแก้ ข้างนอกไม่เปลี่ยน (กลับด้านกับ Go) |
| `demo.php -demo memory` | ทำไม batch job PHP พังตอนข้อมูลเยอะ และ generator ช่วยยังไง |
| `run.sh lifecycle` | PHP ลืมทุกอย่างหลังจบ request จริงมั้ย แล้วแปลว่าอะไร |
| `run.sh ping` | "เริ่มใหม่ทุก request" มีราคาเท่าไหร่ |
| `run.sh cpu` | interpreter ช้ากว่า compiled กี่เท่า บนอัลกอริทึมเดียวกันเป๊ะ |
| `run.sh pool` | ไม่มี connection pool แล้วเจออะไร และทำไมต้องมี pgbouncer |
| `run.sh worker` | ไม่มี goroutine แล้วรับงานพร้อมกันได้เท่าไหร่ |
| `run.sh opcache` | PHP แปลงเป็น bytecode ใหม่ทุก request จริงมั้ย |

## ตัวเลขที่วัดได้จริง

MacBook Air M2 (8 core) / macOS 26.6.2 / PHP 8.5.11 / Go 1.25.0 / PG 17.11 ใน Docker
PHP worker = 10 · Go pool = 10
A1–A3, A5, A6 มาจากการรัน `bash phpdemo/run.sh` รวดเดียวรอบเดียวกัน · A4 มาจากการรันแยก 6 รอบ (ดูข้อจำกัดข้อ 2)

### A1 — ตัวแปรในโปรเซส: Go จำได้ PHP ลืมทุกครั้ง

ยิง `/state` ห้าครั้งติดกัน

```
PHP: [static=1 shared=1 pid=77312] [static=1 shared=2 pid=77308] [static=1 shared=3 pid=77315] ...
Go : [1] [2] [3] [4] [5]
```

`static` ใน PHP ไม่เคยเกิน 1 เพราะ `srv.php` ถูกรันใหม่ตั้งแต่บรรทัดแรกทุก request
`shared` วิ่งขึ้นได้เพราะเก็บไว้ใน PG ซึ่งอยู่ **นอกโปรเซส**
`pid` เปลี่ยนไปมาเพราะ worker คนละตัวรับงาน

| | Go | PHP |
|---|---|---|
| ตัวแปรนอก handler | อยู่ตลอดอายุ server | ตายทุกจบ request |
| in-memory cache | ใช้ได้ | ไม่มีความหมาย ต้องไป Redis |
| singleton / lazy init | สร้างครั้งเดียว | สร้างใหม่ทุก request |
| memory leak ข้าม request | ต้องระวัง | **เป็นไปไม่ได้** |
| data race ระหว่าง request | ต้องระวัง | **เป็นไปไม่ได้** |

สองแถวล่างคือสิ่งที่คนมักลืมพูดถึง — การลืมทุกอย่างไม่ได้มีแต่ข้อเสีย

### A2 — ราคาของการ "เริ่มใหม่ทุก request"

`/ping` ตอบ `pong` เฉยๆ ไม่ทำอะไรเลย · ยิงพร้อมกัน 10 · 3 วินาที

| | req/s | p50 | p99 |
|---|---|---|---|
| PHP (10 worker) | 5,717 | 1.33 ms | 10.26 ms |
| Go | 49,758 | 150 µs | 860 µs |
| **ต่างกัน** | **8.7 เท่า** | **8.9 เท่า** | |

นี่คือ "ค่าเข้าประตู" ล้วนๆ — boot + รันไฟล์ใหม่ + ล้างทิ้ง ยังไม่ได้ทำงานอะไรเลย
Go จ่ายค่านี้ครั้งเดียวตอน start server

### A3 — งานกิน CPU บนโค้ดเดียวกันบรรทัดต่อบรรทัด

`/cpu?n=200000` หาผลรวมจำนวนเฉพาะด้วยลูปซ้อนลูป
(`sumPrimes` ใน `lib.php` กับ `gosrv/main.go` เขียนให้เหมือนกันเป๊ะ)

| | req/s | p50 |
|---|---|---|
| PHP | 37 | 80.9 ms |
| Go | 285 | 12.6 ms |
| **ต่างกัน** | **7.7 เท่า** | **6.4 เท่า** |

วัดอีกรอบได้ 110 ms vs 10.8 ms (10 เท่า) — ช่วงที่เห็นคือ **6–10 เท่า**

แต่ในงาน marketplace จริง เวลาส่วนใหญ่หมดไปกับรอ DB/API ไม่ใช่ลูปแบบนี้
ตัวเลขนี้จึงไม่ค่อยมีผลกับ throughput ของระบบจริงเท่า A4 กับ A5

### A4 — connection pool: สิ่งที่ PHP ไม่มีให้ (ข้อที่สำคัญที่สุด)

`/db` คืน `pg_backend_pid()` · ยิง 300 request พร้อมกัน 10
"คำตอบไม่ซ้ำ" = ใช้ connection ไปกี่เส้น (1 connection = 1 backend process ฝั่ง PG)

วัด 6 รอบแยกกัน (`bash phpdemo/run.sh pool`) — รายงานค่ากลางและช่วงที่เห็น

| | req/s (กลาง) | ช่วงที่เห็น | p50 | connection ที่ใช้ |
|---|---|---|---|---|
| PHP ต่อใหม่ทุก request | 276 | 245 – 439 | ~33 ms | **300** |
| PHP persistent | 2,100 | 1,650 – 2,960 | ~4 ms | 11 |
| Go pool(10) | **10,900** | 5,600 – 12,700 | ~0.8 ms | 10 |
| Go ต่อใหม่ทุก request | 220 | 184 – 351 | ~45 ms | **300** |

คอลัมน์ "connection ที่ใช้" นิ่งสนิททั้ง 6 รอบ — 300 / 11 / 10 / 300 ไม่เคยเปลี่ยน
เป็นหลักฐานที่แข็งกว่าตัวเลข req/s ซึ่งแกว่งตามโหลดเครื่อง

สามอย่างที่อ่านได้จากตารางนี้

1. **Go ที่ต่อใหม่ทุก request ช้ากว่า PHP ที่ต่อใหม่ทุก request — ทั้ง 6 รอบ** (220 vs 276)
   → สิ่งที่ทำให้ช้าคือ "ไม่มี pool" ไม่ใช่ "ภาษา PHP ช้า"
   (pgx คุยกับ server ตอน handshake มากกว่า PDO จึงแพงกว่าเมื่อต้องต่อใหม่ทุกครั้ง)
2. **pool ให้ผลต่างราว 40 เท่า** (276 → 10,900) — มากกว่าความต่างของภาษาใน A2/A3 (6–10 เท่า) หลายเท่าตัว
   จูนผิดจุดแล้วแพงกว่าเปลี่ยนภาษา
3. PHP persistent ได้ 11 connection — ราวจำนวน worker (10) เพราะ worker ตัวเดิมถือเส้นเดิมไว้
   ช่วยได้ ~7.6 เท่า แต่ยังห่าง pool จริงอยู่ ~5 เท่า
   (ยังไม่ได้ไล่ว่าเส้นที่ 11 มาจากไหน — เดาว่า worker ตัวหนึ่งถูกเปลี่ยนระหว่างทาง แต่ไม่ได้พิสูจน์)

**รอบที่พัง (เก็บไว้เพราะมีความหมาย)**
มีหนึ่งในหกรอบที่ PHP ต่อใหม่เหลือ 9 req/s และ error 4 ครั้ง (ได้ connection ไม่ซ้ำ 296 จาก 300)
การต่อใหม่ทุก request ทำให้มีช่วงที่ connection ถูกเปิด-ปิดถี่มากจนพลาดได้
ซึ่งไม่เคยเกิดกับฝั่งที่มี pool เลย

**ทำไมเรื่องนี้ถึงเปลี่ยนสถาปัตยกรรม**

PG เปิด 1 process ต่อ 1 connection (ดู `pgdemo/util.go`) · `compose.yml` ตั้ง `max_connections=50`
บน prod php-fpm ตั้ง `pm.max_children` ที่ 200 ต่อเครื่อง · 10 เครื่อง = 2,000 connection
PG รับไม่ไหว → ต้องมี **pgbouncer** คั่นกลางทำ pool แทน

Go ไม่ต้องมี เพราะคุม pool ได้จากในแอปเอง — นี่คือเหตุผลเชิงสถาปัตยกรรม ไม่ใช่รสนิยม

**กับดักของ persistent connection** (ถ้าจะพูดถึง ต้องพูดให้ครบ)
connection ผูกกับ worker ไม่ใช่กับ request → ถ้า request ก่อนหน้าทิ้ง transaction ค้างไว้
หรือตั้ง session variable ไว้ request ถัดไปที่ได้ worker ตัวนั้นจะเจอสภาพนั้นต่อ
และ PDO ไม่ได้เช็คสุขภาพ connection ให้ก่อนส่งคืน

### A5 — ไม่มี goroutine แล้วรับงานพร้อมกันได้เท่าไหร่

`/sleep?ms=100` จำลองเรียก API ข้างนอกที่ใช้เวลา 100ms

| ยิงพร้อมกัน | PHP req/s | PHP p50 | Go req/s | Go p50 |
|---|---|---|---|---|
| 5 | 43 | 103 ms | 49 | 102 ms |
| 10 | 85 | 103 ms | 96 | 101 ms |
| 20 | 100 | **204 ms** | 195 | 102 ms |
| 40 | 106 | **405 ms** | 390 | 103 ms |

PHP ตันที่ ~106 req/s = 10 worker ÷ 0.1 วินาที เป๊ะตามทฤษฎี
ยิงเกิน 10 ตัว ที่เกินมาไม่ได้ทำงาน แค่ต่อคิว → p50 คูณสองคูณสี่ตามคิวที่ยาวขึ้น
Go โตเป็นเส้นตรงและ p50 นิ่งที่ 102 ms ตลอด เพราะ goroutine ที่รออยู่ไม่กิน OS thread
(เรื่องเดียวกับที่วัดไว้ใน `gmpdemo` — goroutine ที่บล็อกไม่บังคับให้สร้าง M ใหม่)

**แปลเป็นงานจริง:** 1 request ที่รอ API ข้างนอก 3 วินาที = ยึด worker ไปเต็มๆ 3 วินาที
→ งานช้าต้องโยนเข้า queue เสมอ ไม่ใช่ทางเลือก แต่เป็นข้อบังคับของ runtime

### A6 — opcache ช่วยแค่ไหน (ผลขึ้นกับว่ามีโค้ดให้ parse เท่าไหร่)

| endpoint | opcache=off | opcache=on | ต่างกัน |
|---|---|---|---|
| `/ping` (1 ไฟล์ 150 บรรทัด) | 2,712 req/s | 3,764 req/s | 1.4 เท่า |
| `/heavy` (require 300 ไฟล์ ~1 MB) | 80 req/s | 1,532 req/s | **19 เท่า** |

ถ้าวัดแค่ `/ping` จะสรุปผิดว่า opcache แทบไม่ช่วย
Laravel ของจริง autoload ไฟล์หลายร้อยถึงพันไฟล์ต่อ request — ใกล้ `/heavy` มากกว่า

**จุดที่ต้องแยกให้ออก**

| | ข้าม request ได้มั้ย |
|---|---|
| opcache เก็บ **bytecode ที่แปลแล้ว** | ได้ (อยู่ใน shared memory ที่ worker ทุกตัวเห็น) |
| **สถานะของโปรแกรม** (ตัวแปร / object / cache) | ไม่ได้ ต้องไป Redis/DB เสมอ |

เทียบ Go: งาน parse + compile จ่ายครั้งเดียวตอน `go build`
opcache คือการพยายามเลียนแบบเรื่องนี้ แต่ยังต้องเช็ค mtime ของไฟล์อยู่ดี

### B1 — แรม: array ของ PHP แพงกว่า slice ของ Go

เลข 1,000,000 ตัว

| | กินแรม | เทียบ Go |
|---|---|---|
| Go `[]int` | 7.6 MB | 1.0x |
| PHP array key 0,1,2,... (packed) | 16.0 MB | 2.1x |
| PHP array key เป็น string | **70.5 MB** | **9.3x** |

PHP array เป็น ordered hash map เสมอ · ตั้งแต่ PHP 7 มี "packed array" ที่ประหยัดขึ้นมาก
ถ้า key เป็นเลขเรียงติดกัน แต่พอ key เป็น string จะกลายเป็น hash เต็มรูปที่ต้องมี Bucket ต่อช่อง
(ตัวเลข 70.5 MB รวมตัว string ที่เป็น key เข้าไปด้วย ไม่ใช่ overhead ของโครงสร้างล้วนๆ)

**copy-on-write วัดได้**

```
array ต้นฉบับ 200,000 ตัว กิน 4.6 MB
assign เฉยๆ (ยังไม่แก้)   → แรมเพิ่ม 0 B      ← ยังไม่ก๊อป แค่เพิ่ม refcount
assign แล้วแก้ 1 ช่อง     → แรมเพิ่ม 4.0 MB   ← ก๊อปทั้งก้อนตรงนี้
```

และ `memory_limit` เป็นเพดานต่อ **1 request** — ชนแล้ว request ตายทันที ไม่ใช่ช้าลง
Go ไม่มีเพดานแบบนี้ ใช้จนเครื่องหมดแล้วค่อยโดน OOM killer

## ตัวเลขไหนตอบคำถามอะไรได้

| ถ้าโดนถามว่า | ตอบด้วย |
|---|---|
| "PHP ต่างจาก Go ยังไง" | A1 — shared-nothing ต่อ request ไม่ใช่เรื่อง syntax แต่เป็นคนละ execution model |
| "PHP ช้ากว่า Go มั้ย" | A2/A3 ช้ากว่า 6–10 เท่าบน CPU · แต่ A4 บอกว่า pool ให้ผลต่างราว 40 เท่า — จูนผิดจุดแล้วแพงกว่าเปลี่ยนภาษา |
| "ทำไมต้องมี pgbouncer" | A4 — PHP ไม่มีที่ให้ถือ pool เพราะไม่มีโปรเซสที่อยู่ยาว |
| "ทำไม PHP ต้องมี queue" | A5 — งานที่รอ I/O ยึด worker ทั้งตัว ต่างจาก goroutine |
| "แคชใน PHP ทำยังไง" | A1 — ในโปรเซสไม่มีความหมาย ต้อง Redis · A6 — opcache แคชได้แค่โค้ด ไม่ใช่สถานะ |
| "ย้ายจาก PHP ไป Go คุ้มมั้ย" | เทียบ A3 (ภาษา) กับ A4/A5 (สถาปัตยกรรม) — ส่วนใหญ่ปัญหาอยู่ที่อย่างหลัง |

## ข้อจำกัดที่ต้องรู้ก่อนเอาตัวเลขไปอ้าง

1. **ใช้ `php -S` ไม่ใช่ php-fpm + nginx** — ของจริงบน prod คือ php-fpm
   `php -S` กับ `PHP_CLI_SERVER_WORKERS` ให้ *พฤติกรรม* เดียวกัน (N โปรเซส แยกกันคนละ request
   เกิน N แล้วต่อคิว) แต่ไม่ได้ปรับแต่งเพื่อ throughput เหมือน php-fpm
   → ตัวเลข req/s ของ PHP ในนี้เป็น **ขอบล่าง** ของจริงดีกว่านี้ แต่รูปร่างกราฟเหมือนกัน

2. **ตัวเลขดิบแกว่ง 2–3 เท่าระหว่างรอบ** เพราะเครื่องมี container อื่นรันอยู่ (load average ~7 บน 8 core)
   และ **การรัน `run.sh` รวดเดียวทั้งชุดกดตัวเลขของ demo ท้ายๆ ลง** — A4 ที่รันต่อจาก demo อื่น
   ได้ Go pool 2,068–4,161 req/s แต่รันแยกได้ 5,600–12,700
   → ตาราง A4 จึงใช้ค่าจากการรันแยก 6 รอบ ส่วนตารางอื่นมาจากการรันรวมรอบเดียว
   → อ่านเป็น "กี่เท่า" อย่าอ่านเป็น "กี่ req/s" และถ้าจะวัดเอง ให้รันทีละ demo

3. **Go pool ตั้งไว้ 10 เส้นเท่าจำนวน PHP worker** เพื่อให้เทียบกันได้
   ของจริง Go ตั้ง pool ใหญ่กว่านี้ได้โดยไม่ต้องเพิ่มโปรเซส — ข้อได้เปรียบนี้ยังไม่ถูกวัดในตาราง

4. **A3 เทียบความเร็วภาษาด้วยลูปเลขล้วน** ซึ่งเป็นกรณีที่ interpreter เสียเปรียบที่สุด
   งานที่เป็น string / array / การเรียก DB ช่องว่างจะแคบกว่านี้มาก
   และ PHP 8 มี JIT ที่ปิดอยู่ (`jit=off`) — เปิดแล้วงานแบบ A3 จะเร็วขึ้นอีก

5. **ไม่ได้วัดตอน connection เต็ม** — `max_connections=50` ของ pgdemo ไม่เคยถูกชน
   เพราะ PHP จำกัดที่ 10 worker อยู่แล้ว เรื่อง 2,000 connection บน prod ในหัวข้อ A4
   เป็นการคำนวณจากตัวเลข config ไม่ใช่ของที่วัดได้ในนี้

## สิ่งที่ยังไม่ได้ทำ

ชุดนี้โฟกัสที่ runtime อย่างเดียวตามที่ตั้งใจไว้ ยังไม่มี

- **Laravel / Eloquent** — service container, middleware, N+1, migration, queue
  ถ้า marketplace ของเขารันบน Laravel ส่วนนี้คือช่องว่างที่เหลือ
- **PHP เชิงภาษาแบบลึก** — `demo.php -demo syntax` พอให้อ่านโค้ดออก แต่ยังไม่พอให้เขียน feature
- **composer / PSR-4 / namespace** — ตอนนี้ใช้ `require` ตรงๆ ทั้งหมด
- **php-fpm จริง** — ดูข้อจำกัดข้อ 1
